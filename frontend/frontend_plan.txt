00	—	Purpose	&	Source-of-Truth	Hierarchy
This	document	is	the	frontend	equivalent	of	
Dawwarha	—	Backend	Implementation	Plan	v1.0
.	It	follows	the	same	philosophy:	no	page	is	“built”
until	it	is	validated,	tested,	accessible,	responsive,	RTL-correct,	and	integrated	—	not	merely	rendered.	It	is	written	for	four	beginner	Angular
engineers	and	assumes	no	prior	familiarity	with	the	surrounding	documents;	every	non-trivial	concept	is	explained	inline.

explains	how	Angular	consumes	and	visually	represents	those	contracts.	The	source-of-truth	hierarchy	is:

01	—	Executive	Summary
Dawwarha’s	frontend	is	an	Angular	17+	single-page	application	that	gives	the	platform’s	three	user	populations	—	individual	providers/seekers,
community	organizations,	and	platform	administrators	—	a	structured	way	to	publish	resources	and	requests,	review	transparent	rule-based
matches,	coordinate	a	two-sided	handover,	and	see	their	contribution	recorded	as	platform	impact.
The	frontend’s	job	is	narrower	than	it	sounds:	it	does	not	decide	
what
	the	product	does	—	the	Product	Brief	and	Backend	Plan	already	do	that	—
it	decides	how	those	decisions	are	
shown
.	Every	screen	must	make	two	things	obvious	at	a	glance,	per	
DESIGN.md
	Section	2:	what	the	user
can	do	here,	and	what	happens	when	they	do	it.	The	flagship	trust	surface	of	the	whole	product	—	the	Match	Score	with	its	five-signal	breakdown
—	must	never	appear	as	an	unexplained	percentage;	that	single	requirement	shapes	a	large	share	of	Engineer	3’s	work	(Section	10).
The	team	preserves	the	same	four-way	domain	ownership	used	on	the	backend	(Identity,	Supply,	Demand	&	Matching,	Transfer/Trust/Impact),
because	the	two	teams’	domain	boundaries	already	match	one-to-one	with	the	API	surface	each	frontend	engineer	consumes	—	reusing	the	split
minimizes	cross-team	coordination	overhead.
Guiding	principle,	restated	from	the	Backend	Plan:	
do	not	over-engineer	the	MVP.
	No	NgRx	unless	a	specific,	documented	state-sharing
problem	cannot	be	solved	by	a	plain	injectable	service;	no	micro-frontends;	no	custom	design-system	tooling	beyond	a	Tailwind	token	layer.	A
well-structured,	modular	Angular	application	that	four	beginners	can	understand	end-to-end	is	the	actual	deliverable	—	not	an	impressive-looking
architecture	no	one	on	the	team	can	maintain	after	graduation.

	Section	31).

	(

	would	be	equally	at	home	in	an	unrelated
product	(
DESIGN.md
	Section	31).	Every	domain	component	is	built	from	these,	never	from	hand-rolled	markup	that	duplicates	what	a	primitive
already	solves.

	(
core/

	(session	state),	
authInterceptor
,	
errorInterceptor

16	—	Forms	&	Validation
Every	form	in	the	app	follows	
DESIGN.md
	§19’s	anatomy:	
Label	→	Control	→	Helper	text	OR	Error	message	→	optional	Required
indicator.
Covered	forms:
	Register,	Login,	Profile,	Organization	(registration	+	edit),	Resource	(create	+	edit),	Request	(create	+	edit),	Report	creation.
The	two-layer	pipeline,	per	form:
Frontend	Reactive	Form	validators	(immediate	UX	feedback)
								↓
API	submission
								↓
Backend	validation	(the	ONLY	trusted	layer,	Backend	Plan	§15)
								↓
API	error	response:	{	success:false,	error:{	code:'VALIDATION_ERROR',	message,	fieldErrors?	}	}
								↓
errorInterceptor	normalizes	into	ApiError
								↓
Form	component	maps	ApiError.fieldErrors	keys	onto	the	matching	FormControl,	calling	setErrors()
								↓
Field-level	error	renders	exactly	where	a	frontend-caught	error	would	have
This	means	every	form’s	error-rendering	template	code	handles	frontend-caught	and	backend-returned	errors	identically	—	a	
FormControl
’s
error	state	doesn’t	care	which	layer	caught	the	problem,	which	keeps	the	component	simple.
Frontend	validators	mirror	backend	rules	exactly
	(never	invent	a	stricter	or	looser	frontend	rule	than	the	documented	backend	one):	email
format	+	required;	password	minimum	8	characters	(Backend	Plan	Task	1.A	Step	5’s	documented	constant);	resource/request	quantity	>	0;
availability	window	end	>	start;	category	required	and	must	be	a	real	(fetched)	category	id,	never	free	text;	urgency	one	of	the	three	enum	values.
Explicit	non-negotiable:
	frontend	validation	exists	purely	for	UX	—	faster	feedback,	fewer	wasted	round-trips	—	and	is	never	treated	as
sufficient	on	its	own.	Every	form	submission	still	goes	to	the	backend	and	still	handles	a	validation-rejection	response,	even	though	the	frontend
“already	checked.”	This	is	stated	directly	in	Product	Brief	§21	and	repeated	here	because	it	is	a	common	beginner	shortcut	to	skip	backend-error
handling	once	frontend	validation	“already	passes.”
